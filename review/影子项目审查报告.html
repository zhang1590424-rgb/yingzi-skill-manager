一句话结论

安全规则设计得对，但有一处关键交互没落实到真实运行环境里。先修 P0，再处理“反馈不真实”和“界面卡住”这两类 P1 问题。

最值得关注的发现：在打包好的 App 里删除技能时，系统弹出的确认框还没等用户选择，删除就已经执行了。用户点“取消”也照样会删。我在浏览器中按 App 的真实运行方式模拟了这一行为并复现成功（见 P0-1）。

原因（通俗版）：代码把确认框当成“会停下来等用户回答”来写，但在 Tauri 这个桌面框架里，确认框是“先放行、稍后才回答”。代码拿到的不是“是/否”，而是一张“待会儿告诉你”的回执，回执本身被当成了“是”。

好消息：技能还有已启用位置时，后端会拒绝删除，所以误删只会发生在“当前没有应用到任何目标”的技能上。但主库是唯一事实源，删了就没了。

P0-1P0稳定性 · 数据安全

删除技能时，点“取消”也会被删除

已实测复现：按 App 中 dialog 插件的真实行为替换确认框，并让它返回“取消”。结果：确认框被调用 1 次，随后界面立即提示 已删除「lark-doc」，卡片消失。
证据src/App.tsx:1106 写的是 if (!confirm(...)) return;。dialog 插件 2.7.1 会在启动时把 window.confirm 换成异步函数（插件源码 guest-js/init.ts:14，作者注释直说“tauri does not have sync IPC”）。异步函数返回的是 Promise 对象，取反永远为假，所以删除总会继续执行。
额外问题就算异步等到了，插件调用的 plugin:dialog|confirm 命令在 2.7.1 中并不存在（只有 open / save / message），项目权限也只开了 open。换句话说，这个系统确认框在当前 App 里本来就无法正常工作。
为什么测试没发现前端测试运行在模拟浏览器中，没有 dialog 插件，confirm 是同步的；而且 28 个测试里没有一个覆盖删除路径。
修复建议改用项目里已有的应用内 ConfirmDialog（批量操作、覆盖都已经在用），风格也能统一。删除确认里写清“会从主库永久移除，不可撤销”。顺手补一条删除路径的交互测试。
改动成本：小（约 20 行）。影响：彻底消除误删风险，同时让所有危险操作的确认样式一致。
P0-2P0功能 · 状态可信度

详情抽屉里的“收回”不看结果，失败了也提示成功

现象在详情抽屉的“应用状态”里点“收回”，无论后端实际返回什么，都显示绿色的 已收回「xxx」。
证据src/App.tsx:1160-1168 丢弃了 withdrawSkill 的返回报告。而后端在“目标位置不是指向主库的软链接”时不会抛错，只会在报告的 errors 里写一条“未改动”（commands.rs:530）。
为什么是 P0直接违反 PRODUCT.md 里写明的硬规则：“errors 大于 0 时禁止显示 success toast”。用户会以为技能已从某个项目撤下，实际仍在生效。卡片上的同一操作走的是正确逻辑，只有抽屉这条路漏了。
修复建议与卡片保持一致：用 explainReport(report) 决定提示色调和文案；刷新失败时显示“状态暂未核对”横幅。
改动成本：极小（约 5 行）。影响：保证“提示说成功 = 真的成功”。

稳定性

核心是两件事：别让界面卡住，别让失败无声无息。

S1P1性能 · 卡顿

后端命令全部在主线程执行，重活会让整个窗口“转圈”

证据21 个命令全部是普通同步函数（commands.rs）。Tauri 官方文档写明：没有 async 关键字的命令会在主线程上执行（来源）。
哪里最慢get_app_state 每次都扫描主库和所有目标目录；覆盖前的 get_target_fingerprint 会遍历整个目录算哈希；批量操作每处理一个技能就调一次命令。目标放在 iCloud、网盘或外接盘时，卡顿会很明显。
修复建议把命令改成 async fn，或标注 #[tauri::command(async)]。业务代码几乎不用动。
改动成本：小。影响：界面不再“假死”，进度和取消按钮真正可用。
S2P1错误处理

8 个写操作出错时没有任何反馈

涉及操作右键菜单切换 / 新建标签、抽屉内改标签、添加目标、改标签颜色、删除标签、拖拽排序、新建标签（App.tsx 第 360、369、1119、1546、1576、1582、1591、1601 行）。
后果后端报错时，Promise 失败没人处理：界面不提示，用户反复点击也看不出原因。拖拽排序是先改界面再保存，失败后界面顺序和数据库不一致。
修复建议统一套一层：失败时调用已有的 showError；拖拽失败时恢复原顺序。可以抽一个小工具函数，避免每处重复写 try/catch。
改动成本：小。
S3P1批量操作

“重试失败项”永远按“应用”去重试

证据App.tsx:771 写死了 runBatch(again, "deploy")，没有记住上一次是“应用”还是“收回”。
后果批量收回时有几项失败，点“重试失败项”会把它们重新应用，结果和用户意图相反。
修复建议批量结果里保存本次的模式（deploy / withdraw），重试时沿用；按钮文案也写成“重试收回 3 项”。
改动成本：小。
S4P1数据一致性

每次刷新都清空重写部署快照表，而且没有事务

证据storage.rs:653 的 persist_deployments 先 DELETE FROM deployments，再逐行插入，没有包在事务里。它由 load_app_state 调用，也就是说每次查看状态都会写数据库。
后果这张表除了测试之外没有任何地方读取，却让每次刷新都多出一次全表写入。中途出错会留下半张表。dsh 插件也会读写同一个 app.db，读操作附带写操作会增加锁冲突的概率。
修复建议两种选择。产品上暂时不需要部署历史：直接停止写入（推荐，符合“不做操作日志”的约束）。需要保留：放进事务，并且只在应用 / 收回之后写，不在读取时写。
改动成本：小。

交互

整体流程清晰，确认框写清了影响范围，Esc 关闭和焦点循环也都做了。问题集中在键盘可达性和几处状态反馈。

I1P1可访问性

技能卡片不能用键盘打开

证据卡片是一个只绑了 onClick 的 div，没有 tabindex 和键盘事件（App.tsx:932）。实测从搜索框连按 4 次 Tab，焦点停在标签筛选上；卡片本身拿不到焦点。
影响DESIGN.md 要求“弹窗和抽屉必须可键盘关闭”，但入口本身键盘到不了。在“全部技能”视角下，只能 Tab 到卡片里的“详情”按钮，而它在鼠标没悬停时是透明的。
修复建议卡片加 tabIndex={0}、role="button"、Enter / 空格打开详情，并加上 focus-visible 外框。
改动成本：小。
I2P1状态同步

在 App 外改了文件，界面不会更新

现状界面只在启动和自己执行写操作后刷新。用户在 Finder 里删了软链接、在终端里装了新技能，或者 dsh 插件改了标签，回到影子时看到的还是旧状态。全局只有“状态暂未核对”横幅里有一个“重新核对”按钮，平时看不到。
影响用户会基于过期状态去应用或收回，结果落入“冲突”或“未改动”，然后困惑。dsh 插件 README 已经把这条写进了“已知边界”。
修复建议窗口重新获得焦点时静默刷新一次；顶栏加一个刷新按钮，并支持 ⌘R。不需要做文件监听。
改动成本：小。
I3P2防重复点击

卡片按钮的“处理中”禁用状态永远不会生效

证据按钮检查的键是 deploy:${skill.id}（App.tsx:988），实际写入的键是 deploy:${skillId}:${targetId}（第 380 行），两者永远对不上。另外 busy 状态存在 ref 里，变化不会触发重新渲染。
影响重复执行已经被 ref 锁挡住了，不会出事；但按钮在处理中看起来仍可点击，没有视觉反馈。
修复建议用一个 state 集合记录处理中的技能，统一键名格式。
改动成本：小。
I4P2反馈色调

批量操作全部成功时，结果面板也是红色错误样式

证据批量结果复用了 .inline-error-bar（红底，styles.css:2113），不论成功与否。
修复建议全部成功时只弹绿色提示，不显示面板；有失败时才用持久面板，并在标题里写清“3 成功，2 失败”。
改动成本：小。
I5P2筛选逻辑

点击标签栏的“全部”会顺带清掉状态筛选

证据App.tsx:629 的 onClick 同时执行 setActiveTag(null) 和 setStatusFilter(null)。标签和状态是两行独立的筛选，用户只想取消标签时，“只看有问题”的状态也被一起清除了。
修复建议“全部”只清标签；状态行补一个“全部状态”选项，并让两行之间有清晰的分组标题。
改动成本：小。

视觉

整体与 DESIGN.md 的“安静、可信的工作台”方向一致：暖白底、细边框、低饱和状态色，三种窗口尺寸下都没有横向溢出。问题主要在信息密度和提示层的堆叠。

V1P2信息密度

顶部区域偏高，小窗口首屏内容少

实测三个尺寸下工具栏都是 114px 高，第一张卡片从 161px 开始。1040×680 窗口里，顶部占了约 24% 的高度，首屏可见 4/9 张卡。目标上下文里还会再多一行状态筛选和一条底部批量栏。
建议把状态筛选并入标签行的右侧（分段控件），工具栏上下内边距从 20px 收到 14px；分组标题和卡片的间距也可以收紧一档。目标是在最小窗口下首屏能看到 6 张卡（两整行）。
改动成本：中（需要同步更新 DESIGN.md）。
V2P2细节

目标下拉的箭头是旋转的“‹”字符，展开时不变化

证据App.tsx:583 用文本字符 ‹ 加 rotate(-90deg) 模拟下拉箭头；styles.css 里没有展开态样式。字符在不同字体下粗细和基线都不一致。
建议换成和设置图标同一套线性 SVG 的 chevron，展开时旋转 180°。触发按钮补上 aria-expanded，下拉项改成 button 元素，以便键盘和读屏软件识别。
改动成本：小。
V3P2提示层

错误条、批量结果和提示都钉在同一位置，会互相盖住

证据.toast 和 .inline-error-bar 都是 position:fixed; top:60px 水平居中（styles.css:1554 / 2113）。批量结果面板和普通错误条用的是同一个样式，同时出现时会完全重叠，正好盖住目标下拉和搜索框。
建议持久类信息（错误、批量结果）放进内容区顶部的文档流，和“状态暂未核对”横幅排在一起；只有短暂的成功提示浮在上层。这样多条信息会自然向下排列，不会互相遮挡。
改动成本：中。

F1P1目标管理

项目文件夹被移动或删除后，界面没有任何提示

证据后端为每个目标计算了 pathExists / targetExists / rootExists，前端 transform.ts 也接收了，但 App.tsx 中一次都没有使用。
后果用户改名或移动了项目文件夹，下拉菜单和设置里仍然正常显示这个目标；直到点“应用”才收到“目标路径不存在”的报错。DESIGN.md 要求“项目根路径不存在时阻断应用并引导到设置处理”，这里只做了一半。
建议下拉和设置里给失效目标加灰色“路径不存在”标记；选中失效目标时，用横幅说明原因并提供“在设置中移除”入口，批量操作按钮置灰。
改动成本：中。
F2P1覆盖规则

同一个“有问题”的技能，卡片能覆盖、抽屉不能覆盖

证据抽屉用正则 /冲突|失效|broken|conflict/ 匹配问题描述来决定是否显示覆盖按钮（App.tsx:1239）。但后端实际返回的文案是“目标位置已有同名内容”“软链接目标不存在”“目标位置已有指向别处的软链接”等（storage.rs:1020-1034），没有一个包含这些关键词。结果是抽屉里永远不出现覆盖按钮。
反过来卡片上对所有“有问题”的技能都显示覆盖按钮（App.tsx:994），包括“目标技能目录不存在”“无法读取”这类本不该一键覆盖的情况（后端会拒绝，但用户先得走完一次确认流程）。
建议不要靠匹配中文文案做判断。后端已经有 7 种细分状态（Conflict / Broken / PathMissing 等），直接把细分状态或一个 can_overwrite 布尔值传给前端，卡片和抽屉共用同一条规则。界面仍只展示 3 种状态，符合“不在 UI 展示 7 种细分状态”的约束。
改动成本：小。
F3P2小功能

搜索不匹配标签；重复添加同一目标会静默覆盖
